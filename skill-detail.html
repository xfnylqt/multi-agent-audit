Skill · 任务编排 / 多 Agent 审计

技能罗盘

一个「skill 路由器 + 多 Agent 审计员」。核心理念：有现成的轮子，就别从零造——遇到任务先找现成 skill 复用，同样的活儿别人早干过，直接调用最省时、最省 token。你描述任务，它告诉你用哪个 skill；本地没有就上 GitHub 搜候选；你说"审计一下"，再派几个 agent 从多角度帮你查漏。

形态 纯 skill · 零依赖

理念 别重复造轮子 · 省 token
💡 有现成的轮子，就别从零造。AI 从零写代码 / 方案要烧掉大量 token；而直接复用别人早写好的 skill，几乎是零成本。本地命中 = 零 token，去 GitHub 找 = 一次搜索——都比硬造划算，效率也高得多。

能做什么

  • 断网跑 Layer 1：按关键词把任务匹配到本地已装 skill，零 token、毫秒级
  • 本地没命中跑 Layer 2：去 GitHub 搜对口 skill 仓库，列带 star / 描述的候选
  • 你点名"审计"时跑 Layer 3：派 2–4 个 agent 分头做、再交叉核对

不做什么

  • 不做语义级精准推荐——只做关键词级匹配
  • 不在你没要求时自动开多 Agent；你点头它才派
  • 不替你拍板装哪个 skill——候选列给你，挑哪个由你定
为什么需要多 Agent 审计
AI 不是全知全能——它会幻觉、会自信地胡说八道。一个人容易被骗，一群人互相盯着就不一样了。
🤖 AI 有时候会「骗人」：编造不存在的 API、拼错文件名、把错的当对的讲得头头是道。
🤝 多个 AI 从多角度交叉核对，漏判和翻车的概率大幅下降——这就是 Layer 3 存在的理由。

单一 AI 的坑

  • 幻觉：凭空造出不存在的库 / 接口 / 参数，还一脸理直气壮
  • 一旦方向跑偏，整条链路都跟着错，没人拉它一把
  • 错误被当作事实输出，你很难一眼识破
  • 安全、边界、异常处理这类"隐性"问题最容易被漏掉

多 Agent 互审的好处

  • 分头实现 + 互相审查，彼此抓漏、互相兜底
  • 实现 / 审查 / 安全 多个视角并行，盲区被覆盖
  • 多数一致才收敛，单点翻车不再"一错到底"
  • 交付「改动 + 风险清单」，哪儿动了、有啥风险你看得见

示例

用户："我想把抖音小店的订单按渠道汇总成表"

→ 命中 webapp-e2e-hotfix，派 3 个 agent（实现 / 安全 / 边界）交叉比对。

安装 & 使用
把目录放进用户级 skill 目录即生效，无需 pip install；两条命令纯标准库、离线可用。
① 安装
把整个文件夹放进 ~/.workbuddy/skills/multi-agent-audit/ 即生效。
发布到 GitHub 后可一键克隆：
git clone https://github.com/mcc/multi-agent-audit.git ~/.workbuddy/skills/multi-agent-audit
② Layer 1 · 本地路由
python route_local.py "把抖音小店的订单按渠道汇总成表" --top 6
③ Layer 2 · GitHub 兜底
python gh.py "给 PDF 加水印的 skill" --limit 6
覆盖范围与边界：Layer 1 只扫你主动管理的用户级 skill（~/.workbuddy/skills/）；Layer 2 是关键词级而非语义推荐；两条命令纯标准库、离线可用，GitHub 那条联网失败会返回 {"ok":false} 并优雅降级，绝不让主流程崩。
背景：最早的 1.x 是常驻 daemon，靠 CDP 注入往聊天界面塞悬浮球 + 面板，强依赖浏览器远程调试端口，白屏 / 弹窗错位 / CSP 拦截都出过。本版（2.0）砍掉全部 UI 与常驻依赖，改成纯 skill —— 不碰任何界面、不需调试端口，装上即用。
